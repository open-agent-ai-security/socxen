Summary
The Agent (as modeled)

socxen is a SOC analyst assistant that runs inside an analyst's own terminal session. Three prompt-driven skills - one that works a single alert or case end to end, one that sweeps the open case queue, and one that diagnoses noisy detection rules - reach an Exabeam New-Scale tenant through a small local bridge the plugin ships and starts itself. Its only high-volume untrusted input is tenant telemetry: alert names, event fields and case notes whose text is written, in part, by whoever generated the activity being investigated. Its consequential capabilities are narrow and well chosen - it can open cases, write notes, dismiss an alert, close a case, and send mail from the platform; it has no containment reach at all. Three deterministic controls sit on the real path rather than in a design document: a permission gate that ships active and classifies every platform tool, a screen on everything the agent reads, and a masking pass on everything it writes. A sustained first-party red-team programme, hash-pinned dependencies and tests that pin the governance tiers to the documentation make this a materially stronger posture than most agents of its shape.

Priority Threats (led by attack paths)

Three things deserve attention before the next deployment. First, outbound mail: the platform exposes a tool that mails an HTML fragment to any address the model produces, it is set to prompt rather than to refuse, and it is the one write the masking pass deliberately skips - so a phishing link or active markup planted in an alert can be quoted into a mail body and arrive live at whoever is on the list, outside the two audiences the agent is supposed to talk to. Second, the gate that everything else leans on is carried by a plain call to the system Python interpreter with no fallback; the decision logic itself never fails open, but on a workstation without that interpreter the gate simply does not run, and the installer's own check reports that as a minor warning rather than as the gate being off. Fix the invocation and re-tier or neutralize the mail tool, in that order.

After that, the residual risks are quieter but real. A case dump too large for the session gets written to a plain file on the analyst's laptop, unredacted and unpruned, and two of the skills are told to go and read it back - the one place raw tenant evidence leaves the tenant and stays. The queue sweep's promise to write nothing is prompt text only, and the two writes it forbids are exactly the ones the gate waves through without a prompt. The remote server's own tool descriptions are pulled into the model's context with no screening and no version pin, and they already contain text telling the caller to ignore the user - today that costs a wasted context window, but nothing would flag it if the descriptions changed. And the shipped documentation still contradicts itself about whether the gate survives permission-bypass modes, which is the one question an operator will actually ask.
