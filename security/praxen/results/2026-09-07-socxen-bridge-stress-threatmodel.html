Summary
The Agent (as modeled)

socxen is a three-skill SOC analyst suite that a human analyst drives from an interactive Claude Code or Codex session against a single Exabeam New-Scale tenant. Its reasoning lives in prompt files rather than code: the investigation loop is a skill the model follows, its only tool surface is a bundled local bridge that proxies every call to the remote Exabeam MCP under an OAuth token minted from a plaintext credential file on the analyst's workstation, and its only consequential capabilities are the platform's four non-destructive writes plus a human-confirmed platform email. Everything it reasons over — alert fields, event records, case notes, and the remote server's own tool descriptions — is written by whoever generated the logged activity, so tenant telemetry is the untrusted input surface and the dismiss-or-close write is the consequential one. Three enforcement layers stand there: a permission hook that ships active with the plugin, a deterministic screen on everything read and a deterministic neutralizer on everything written, and two default-on audit trails.

Priority Threats (led by attack paths)

Two chains deserve action first. Content planted in an alert or case can steer the investigation to the point where the analyst approves a dismissal, and the write that follows replaces the record's existing description, name and closing reason wholesale — nothing reads or preserves the prior text, so a legitimate approval quietly destroys evidence. Separately, the remote platform's own tool definitions reach the model unscreened while every tool result is screened; the project's own reference material records that those descriptions already tell the caller to ignore user requests, so a changed or compromised upstream definition is the single ingress the bridge does not defend — and a tool it advertises that the shipped tiers never classified draws a prompt rather than a refusal, leaving one operator yes between an attacker and a change to the tenant's detection content.

Three weaknesses in the assurance around that. The installer tells the operator the human-in-the-loop gate has dismiss and close covered without ever checking that the installed copy carries the hook, and it downgrades a failed update to a warning, so an offline install can end up gate-less behind a green line. Turning the audit trail off produces no disclosure at all, while every other way it can stop announces itself — the record can disappear without anyone noticing. And the file holding the tenant key and secret is protected by advice rather than by the installer, which reports a wrong file mode and never fixes it, on a credential that carries the tenant's full read and triage-write reach. Set against that, the deterministic parts of this system are genuinely strong: the gate fails closed on every branch, an unrecognized tool is treated as a write, the dependency tree is hash-pinned and audited on every build, and both audit trails record identifiers and enumerations only, so a planted payload cannot ride into them.

Attack Paths
Text planted in a tenant alert ends with the analyst approving a write that destroys the case's existing record
  1. Tenant telemetry (alert / event / case free text) Alert, event and case free text is authored by whoever generated the logged activity — attacker-influenceable, unauthenticated as evidence, and indistinguishable from platform output by formatting alone.
  2. Remote Exabeam New-Scale MCP The platform returns that text verbatim as the result of the read tools the investigation runs.
  3. Bundled Exabeam MCP bridge The bridge screens results for unambiguous smuggling code points only; instruction-shaped prose and a planted 'baseline' pass through unchanged and unlabeled.
  4. socxen skill suite (investigation loop) The loop reasons over the planted content as evidence and reaches the false-positive verdict it was steered toward; only skill prose stands against it.
  5. Host agent session (Claude Code / Codex) The model proposes the dismiss or close; the bundled hook asks, and the analyst — reading a report shaped by the planted content — answers yes.
  6. Bundled Exabeam MCP bridge [PRAX-2026-09-07-003] The approved write is forwarded with the record's description, name and closing reason as wholesale replacements; nothing reads or preserves the prior value, so the existing free text is destroyed along with the disposition change.
A changed upstream tool definition steers the agent into a detection-content change the deny list never named
  1. Remote Exabeam New-Scale MCP [PRAX-2026-09-07-001] The remote server supplies the tool names, schemas and parameter descriptions; that channel has no integrity check, no allowlist and no change detection, and its own vendor text already directs the caller to ignore user requests.
  2. Bundled Exabeam MCP bridge [PRAX-2026-09-07-001] list_tools returns the upstream definitions verbatim — the one ingress path the bridge does not canonicalize, unlike every tool result.
  3. socxen skill suite (investigation loop) [PRAX-2026-09-07-001] The definitions land in the model's context as authoritative tool documentation, countered only by a prose instruction not to comply.
  4. Host agent session (Claude Code / Codex) [PRAX-2026-09-07-004] The model calls the newly advertised tool; it is not among the deny tier's enumerated spellings, so the gate asks rather than denies and an operator yes releases it.
  5. Bundled Exabeam MCP bridge [PRAX-2026-09-07-004] The bridge treats the unclassified tool as a write — neutralized and audited — and forwards it to the tenant.
  6. Remote Exabeam New-Scale MCP [PRAX-2026-09-07-004] The change lands on the tenant's detection content, the durable state the remit says must never be reachable under any spelling.

Extraction Notes
lane_fit: Two strains, both resolved conservatively. The two audit trails are local files written in-process (an imported module inside the bridge, and the PreToolUse hook) but are placed in external_deploy because the lane table names telemetry sinks there rather than with the writing process. The shipped permission-tier source is read by two processes in different lanes — the hook in client_adapters and the bridge in tools_mcp — so it is placed in agent_core as the shipped governance policy rather than arbitrarily in one enforcing lane. Everything else is clean.
omissions: Arbitration divergences (KB wins): PRAX-2026-09-07-001's stored tags list LLM01 before ASI04, but the Agentic KB's compound-signal row for a poisoned or unverified third-party tool description makes ASI04 the primary, so the untrusted-ingress threat is tagged ASI04. PRAX-2026-09-07-008's stored tags list LLM02 before ASI03, but the mechanism producing the harm is credential scope and at-rest agent identity — explicitly ASI03's subject under the Agentic KB mechanism rule and cross-KB precedence — so the secret-material threat is tagged ASI03. Could not cite: the host agent's spill file for an oversized tool result (the remit's Open Question 9 residual) has no implementing or referencing code or config in the workspace, so no node was created for it. Modelling choices: the three skill prompts are one orchestrator node, per the directory-family rule (parallel same-role markdown with no enumerating construct); the model node is named for the remit's declared primary model although it also stands for the Codex host's model tier; and both attack paths revisit the bridge and the remote MCP node because the proxy architecture carries the inbound and outbound legs over the same two edges.
