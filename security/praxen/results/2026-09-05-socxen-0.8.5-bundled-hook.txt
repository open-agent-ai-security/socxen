BEHAVIOR SUMMARY
------------------------------------------------------------------------------
The dominant pattern here is a genuinely load-bearing deterministic layer with
a narrow, allowlist-shaped perimeter — and the gaps all sit exactly where that
perimeter ends. gate.py, neutralize_output.py and canonicalize.py are real
controls on the real path, active on install and fail-closed where it matters,
and a sustained first-party red-team programme proves they are load-bearing
rather than decorative. But each is bounded by a hardcoded list: the
write-side neutralizer covers five tool names and six field names, so
exabeam_send_email's HTML body leaves un-defanged; the read-side canonicalizer
screens tool results while list_tools() proxies the remote server's tool
descriptions into context unscreened and unpinned; and the gate itself, which
never fails open once it runs, is invoked as python3 gate.py with nothing
making that invocation fail-closed. No compound escalation was warranted — the
human ask on every consequential write is what breaks the one chain the
evidence supports.

HIGH FINDINGS
------------------------------------------------------------------------------
  PRAX-2026-09-05-001  The bundled gate never fails open once it runs, but
            nothing makes its invocation fail-closed — no python3 on PATH
            means no gate.
      Action 1: In `plugin/hooks/hooks.json`, wrap the command so a missing or
                failing interpreter still blocks — e.g. invoke a small shell
                wrapper that emits a `deny`/`ask` PreToolUse decision on
                stdout and exits 0 when `python3` cannot be resolved, rather
                than letting the hook error into a non-blocking path.
      Action 2: In `plugin/preflight.sh`, promote a missing python3 from
                `warn` to `fail` with text naming the consequence directly —
                the bundled dismiss/close gate cannot execute — and add a
                positive check that runs `gate.py` once against a synthetic
                event and asserts the returned `permissionDecision`.

  PRAX-2026-09-05-002  exabeam_send_email sends tenant content as HTML to
            arbitrary recipients — a channel the remit never authorizes, and
            the one write the neutralizer skips.
      Action 1: Move `exabeam_send_email` to the `deny` tier in
                `settings.snippet.json` and `disabled_tools` in
                `.mcp.codex.json` until an HTML-aware neutralizer exists, or
                add the tool's `body` and `subject` to `_DEFANG_FIELDS` with
                an HTML-mode pass that strips anchors, scripts and event
                handlers rather than the markdown-shaped rules.
      Action 2: Reconcile the remit and the shipped surface: either add an
                outbound-mail row to Approved Communication Channels with a
                recipient allowlist enforced in
                `plugin/connector/exabeam-mcp-bridge.py`, or remove the tool
                from the governed surface entirely.

  PRAX-2026-09-05-003  The bridge screens tool results but proxies the remote
            server's tool descriptions into model context unscreened,
            unpinned, and already carrying instructions.
      Action 1: Run tool metadata through the same screening as results — call
                `canonicalize()` on each tool's name, description and
                parameter descriptions in `list_tools()` in
                `plugin/connector/exabeam-mcp-bridge.py`, and surface any
                strip to the audit trail.
      Action 2: Pin the tool surface: ship the expected tool-name set (the
                tier map already enumerates it) and have the bridge log and
                flag any tool whose name or description hash differs from the
                recorded baseline, so a silent redefinition is visible rather
                than trusted.
